# Benchmark-Solver Primitives and the SLM-Uplift Thesis

Last updated: 2026-07-03. What primitives let a system solve agentic / software-bench / LeetCode / competitive-
programming work by RETRIEVING and COMPOSING, not generating from scratch — and why a small specialized model
(Gemma 4 Coder + LoRA) doing that can beat a frontier model's one-shot. Companion to the consumption benchmark
(`scripts/run_primitive_consumption_benchmark.py`), the solver demonstrator
(`scripts/demo_solver_route_composition.py`), and `docs/OPERATIONS-BIBLE.md`.

## The thesis (owner 2026-07-03)

> A small specialized model that grabs proven primitives, orders them by edge compatibility, and composes code can
> outperform one-shot/multi-shot frontier generation — quicker, cheaper, and more finely monitored/structured —
> given a large enough universe of working primitives with real edge definitions, edge contracts, and edge matching.

Why it can win, stated as mechanism (not yet a measured claim):
- **Bounded vs unbounded.** One-shot generation is unbounded — the model writes the whole solution and can hallucinate
  API calls, off-by-ones, wrong complexity. Composition is bounded — the model picks from a finite set of proven,
  contract-checked primitives and emits only the glue. The error space shrinks to "wrong selection/ordering," which
  is cheap to verify and repair.
- **Tokens.** One-shot burns output tokens proportional to solution size every time. Primitive-first reads compact
  edge cards (input_edge + output_edge + blackbox ≈ 150-300 tokens) and emits per-step glue. Amortized across a
  benchmark suite, the token curve is far below one-shot (the consumption benchmark estimates 67-98% per task).
- **Monitoring/structure.** A composed route is N receipted steps, each a verifiable primitive with a proof
  obligation — vs one opaque generation. You can localize a failure to a step and repair only that step
  (the `repair` meta-primitive), never regenerate the whole.
- **Small-model reach.** Selection + ordering + glue is a NARROW task a small model + LoRA does well; the hard part
  (the algorithm) is precomputed in the primitive. This is the [[small-models-need-narrow-scope-and-deterministic-harnesses]]
  principle applied to coding benchmarks.

## The solver layer: 6 meta-primitive families (single source: SOLVER_META_PRIMITIVES in the demonstrator)

These sit ABOVE the algorithm/capability primitives and turn "retrieve" into "solve":

| meta-primitive | edge | role |
| --- | --- | --- |
| `decompose` | ProblemStatement+Constraints → TaskSignature+SubgoalGraph | parse problem, classify algorithm family, extract I/O + constraints + complexity budget |
| `select_match` | TaskSignature+PrimitiveRegistry → CandidateBundle+EdgeMatchScores | edge-match the signature against the registry; rank candidates by compatibility |
| `order_compose` | CandidateBundle+SubgoalGraph → OrderedRoute+PlanLock | chain candidates output_edge→input_edge into a dependency-valid ordered route |
| `emit_code` | OrderedRoute+TargetLanguage → CodeArtifact+CompileReceipt | instantiate each ordered primitive to code, bounded per-step |
| `verify_run` | CodeArtifact+ExampleFixtures → TestReceipt+ComplexityReceipt | run examples + edge cases, check complexity budget |
| `repair` | TestReceipt+FailureClass → RoutePatch+NegativeMemory | localize to the failing step, swap/repair only it, never regenerate all |

`order_compose` is the load-bearing step — it's demonstrated live in `demo_solver_route_composition.py`: seed at a
SOURCE primitive (input not produced by any other retrieved card), then greedily append the card whose input_edge
best chains from the current output_edge. `edge_chain_strength > 0` means the retrieved primitives actually
COMPOSE (not merely each relevant) — the sharp signal beyond raw retrieval coverage.

## What primitives each benchmark family needs (the demand map)

- **LeetCode / HumanEval / MBPP / EvalPlus** → the classic ALGORITHM + data-structure universe: sorting/searching,
  graph, dynamic-programming, tree/heap/trie/segment-tree/Fenwick, string algorithms, numeric/math, hashing/sketches,
  computational geometry, competitive patterns (two-pointer, sliding window, prefix-sum, binary-search-on-answer,
  backtracking, bitmask, monotonic stack). Generated by the `algorithm-swe-gap-fill` lane (uc07alg).
- **Competitive (Codeforces/AtCoder/ICPC/USACO/Project Euler/LiveCodeBench)** → the above PLUS problem archetypes:
  constructive, game-theory (Nim/Grundy), interactive, combinatorics/probability, number theory, max-flow/matching,
  string hashing/suffix automaton. Game-theory is the one archetype without a dedicated generation family yet.
- **SWE-bench** → repo-repair primitives: reproduce-from-issue, fault localize, minimal-patch, test-run+diff,
  regression guard, add-test-for-contract, refactor-preserving-behavior, dependency/import fix + code-analysis
  (AST parse, call-graph, complexity, lint).
- **Terminal-Bench** → CLI/runtime wrappers: file ops, subprocess, exit-code contracts, env setup.
- **BFCL / AppWorld / GAIA / WebArena** → agentic primitives: tool-schema-validate, tool-select, argument-bind,
  abstain-when-no-safe-tool, multi-step API-state transition with idempotency + receipt, browser action/extract.
- **MLE-bench / DS-1000 / BigCodeBench** → data-science pipeline + library-API primitives (train/val split, metric
  parse, feature engineering, submission validate, pandas/numpy/sklearn call contracts).
- **BEIR** → retrieval primitives (chunk/embed/index/retrieve/rerank/ground).

## How to measure it (already runnable)

- **Consumption benchmark** (`--run`): 56 tasks across 20 public families → solver-route coverage, stringability
  (distinct composable primitives), thin-coverage soft gaps, estimated token savings. Meta-cards excluded so
  uncovered = real gap. This is the "can we retrieve + is there enough to string" measurement.
- **Solver demonstrator** (`--run`): composes an actual edge-chained route per coding task and reports
  `edge_chain_strength` + `composable` + token savings vs one-shot. This is the "can we actually order + compose"
  measurement.
- **The next rung (planned, honest):** a live paired-arm run — small model + primitive-route vs frontier one-shot on
  real benchmark tasks with executed tests — promotes the token/quality claim from ESTIMATE to MEASURED. Until then,
  all savings/uplift numbers stay candidate/estimate-labelled.

## The LoRA lane

The small-model selection/ordering/emit task is exactly what a `primitive_route_composer_adapter` LoRA specializes:
train on (task_signature, retrieved_candidate_bundle) → (ordered_route) from the benchmark run receipts. The adapter
records (base_model_ref=gemma-4-coding, training_data_lineage=solver-demo + benchmark receipts, eval_task_set=the 56
benchmark tasks, promotion_receipts). It competes against rule-based ordering (the demonstrator's greedy composer)
and frontier one-shot — metrics decide. Never Gemma 3.
