# aidoneright-yc-applications

A CONTEXT repo in the **AI Done Right** multi-repo org: the Y Combinator (and other accelerator)
**application artifacts** — application drafts, founder and video answers, readiness scoring, and the
demo storyboard. It is "context in a repo": the application material, kept separate from product code. It
holds **no product code** and is never imported — humans and agents *read* it for grounding.

## What this repo is

It exposes, as its published interface (source: `../dev-rules-context/contracts/surface-registry.json`):

- **yc-application** — the Y Combinator / accelerator application draft: answers, founder story, video
  script.
- **yc-readiness** — YC-readiness scoring across the dimensions gate. **Computed** by
  `scripts/yc_readiness.py` (which stays in `shared-backend-components`), never asserted here.
- **demo-storyboard** — the YC / demo-day storyboard: the live capability demo sequence.
- **founder-answers** — reusable answers to common YC / investor founder questions.

## How it fits

Dependency direction is fixed by `../dev-rules-context/contracts/surface-registry.json`:

- **This repo may consume:** `dev-rules-context` (standards, contracts, checkers, `_shared`) and
  `aidoneright` (the parent brand's public face: `portfolio-site`, `brand`) — via their published interface
  only, never their source. It depends on no substrate or product.
- **This repo is consumed by:** nobody yet (`consumed_by: []`). Keep the exposed interface stable for when
  a surface begins to reference it.

The authoritative, machine-readable edges live in `EDGES.md` (generated by the edge-graph-generator from
the surface registry); the neighbor view is `context/edges.md`.

## A note on what stays code-coupled

`yc-readiness` is **computed**, not stored: `scripts/yc_readiness.py` reads its target doc
(`docs/strategy/yc-readiness-and-prep-2026.md`) and the deck data (`architecture/yc_demo_storyboard.json`,
`architecture/teleon_pitch_deck.json`) by path. Those inputs, and the `docs/goals/yc-readiness-loop.md`
dev-loop entrypoint, stay in `shared-backend-components` so the code keeps working; `context/blackbox.md`
records exactly where each lives. This repo owns the human-authored **application draft**.

## Layout

- `CLAUDE.md` — the agent operating manual (filled from the org template; inherits the 8 standards).
- `EDGES.md` — this repo's cross-repo contract: neighbors' published edges, nothing of their internals.
- `context/blackbox.md` — what this repo owns (its exposes, described) and its current contents + pointers.
- `context/edges.md` — the neighbor view and the boundary rule.
- `context/` — the application material itself, added as it lands.
- `README.md` — this file.

Inherited standards, the shared glossary/config, and the portable checkers live in the sibling
`../dev-rules-context/` repo — this repo does not re-declare them.

**Context-only, no product code.** Nothing here is importable; surfaces reference it for grounding.

## How to work in it

1. Read `../dev-rules-context/standards/README.md`, then `CLAUDE.md`, then `EDGES.md` / `context/edges.md`.
2. This is context-only — add application drafts and answers; do not add product code, and do not import a
   neighbor's source.
3. **No confidential financials or real investor PII.** Public / synthetic only. `yc-readiness` numbers are
   computed by `scripts/yc_readiness.py`, never asserted in prose.
4. Design / brand / strategy / pricing claims need clear owner intent or strong corroboration
   (change-verification law), never a unilateral single-agent call.
