GTM launch guide

From repo to production, domains, email, and customer-ready demos.

A step-by-step operating guide for launching the three-site platform story: AI Done Right as the parent brand, Baltor as the paid context-control product, and OpenHubForAI as the open builder funnel.

Launch principle

Do not treat GTM as a landing page exercise. The launch is production readiness plus a coherent buyer path: credible domains, working demos, transactional email, analytics, support, billing, docs, and a repeatable pilot motion.

1. Set up the environments

Keep the same product story across local, development, staging, and production. The difference should be data, secrets, observability, and traffic policy, not code behavior.

Local/dev

Developer loop

Run all three sites locally, use synthetic data, local queue, local models, and no production credentials.

Staging

Buyer rehearsal

Use production-like cloud services, test domains, transactional email sandbox, test billing, and seeded demo corpora.

Production

Customer path

Use live domains, monitored services, real auth, support, billing, backups, security headers, and audit logs.

2. Step-by-step launch checklist

Work through these in order. Each step should have an owner, a verification command or dashboard, and a rollback path.

01

Repository and branch policy

Protect the main branch and make releases traceable.

  • Create `main`, `develop`, and release branches or a trunk-based equivalent.
  • Require PR checks for validation, docs build, and site smoke tests.
  • Add CODEOWNERS for web, infra, schemas, and docs.
  • Tag releases as `web-YYYY.MM.DD-n` or semver once customer-facing.
ProofBranch protection is enabled, CI blocks broken builds, and a release tag can be traced to deployed artifacts.
02

Local development

Make a new contributor productive in one session.

  • Document `python3 -m scripts.showcase` for one site and `scripts/serve_all_sites.sh` for all three.
  • Keep `OH_PRODUCT` as the product selector.
  • Run worker self-tests and admin demo locally with synthetic data.
  • Use local Ollama/OpenAI-compatible endpoints only through provider-neutral env vars.
ProofFresh checkout can serve AI Done Right, Baltor, OpenHubForAI, and `/admin-demo` without production secrets.
03

Cloud accounts and projects

Create separate dev, staging, and production projects.

  • Choose the first hosting path: Cloudflare Pages/Workers, Vercel/Render, or Cloud Run/Kubernetes.
  • Create separate projects/accounts for staging and production.
  • Set IAM groups for admin, deploy, read-only, and billing.
  • Turn on budget alerts before connecting metered model APIs.
ProofEach environment has separate credentials, budgets, and audit logs.
04

Staging deployment

Deploy the exact three-site story before touching production domains.

  • Deploy `context-is-everything`, `baltor`, and `openhubforai` as separate web doors.
  • Point each to the shared backend API where needed.
  • Seed staging with non-PII demo data and sample context runs.
  • Run health checks for `/`, `/api/health`, and `/admin-demo/`.
ProofStaging URLs show the correct brand marker and load the right product folder.
05

Production services

Bring up durable services only after staging is clean.

  • Provision Postgres/pgvector for operational records, facts, sources, and vectors.
  • Provision object storage for raw uploads, extracted text, packages, and audit artifacts.
  • Provision Redis or managed queue for worker lanes.
  • Configure backups, retention, encryption, and restore tests.
ProofRestore test succeeds and service credentials are not shared with staging.
06

Domains and DNS

Connect clean customer-facing routes.

  • Point parent domain to AI Done Right.
  • Point `baltor.ai` or product domain to Baltor.
  • Point OpenHubForAI domain to OpenHubForAI.
  • Configure HTTPS, redirects, canonical hostnames, HSTS when ready, and DNS monitoring.
ProofEach domain returns 200, correct brand marker, valid TLS, and expected canonical URL.
07

Auth, CRM, and billing

Make interest capture and pilot conversion real.

  • Add waitlist/demo request forms with spam protection.
  • Route leads into CRM with source, campaign, and requested use case.
  • Enable test billing for pilots and production billing for paid contracts.
  • Add account roles for admin, curator, viewer, and security reviewer.
ProofSubmit a demo request and confirm CRM record, confirmation email, and internal alert.
08

Transactional email

Set up email before inviting design partners.

  • Choose provider and create separate staging/production sending domains.
  • Configure SPF, DKIM, DMARC, bounce handling, and suppression lists.
  • Create templates for invite, magic link, run complete, export ready, review required, billing receipt, and support reply.
  • Log every outbound email event against tenant and run ids.
ProofSeeded staging user receives every template; production domain passes authentication checks.
09

Observability and operations

Know what is running, queued, slow, broken, or expensive.

  • Track web latency, API health, queue depth, oldest job age, worker failures, and model/API spend.
  • Add run ledger, worker traces, and audit packet download.
  • Create alerts for site down, queue stuck, email failures, DNS/TLS failures, and spend spikes.
  • Document incident owner and rollback command.
ProofStaging incident drill triggers alert, captures logs, and restores service.
10

Security and compliance baseline

Do enough to be credible with enterprise buyers.

  • Use secret manager, not repo/env files, for production secrets.
  • Set CSP, security headers, CORS policy, rate limits, and upload size limits.
  • Document data retention, subprocessors, backups, access review, and deletion path.
  • Prepare a lightweight security packet for design partners.
ProofSecurity packet, data-flow diagram, and access review are current before production pilots.
11

Demo and pilot packaging

Turn the product into a repeatable buyer motion.

  • Create one polished Baltor admin demo with upload, processing, outputs, and downloads.
  • Create one OpenHubForAI path showing a governed harness consuming trusted context.
  • Create one parent narrative page explaining why context is the bottleneck.
  • Prepare a 2-week paid pilot offer and success metrics.
ProofSales call can move from parent story to Baltor demo to pilot scope without switching narratives.
12

Production cutover

Launch only when staging has rehearsed the full path.

  • Freeze release candidate and tag it.
  • Run smoke checks on all three production domains.
  • Send test transactional emails from production domain.
  • Verify analytics, CRM, billing, support inbox, backups, alerts, and rollback.
ProofLaunch checklist is signed off with URLs, test evidence, and owners.

Rule of thumb

Launch the parent story only when the buyer can click into Baltor, see a credible context-control demo, request a pilot, receive transactional email, and land in the CRM. Launch OpenHubForAI as the open funnel, not as a competing generic agent builder.
