CI/CD platform review

Keep GitHub Actions — but don't let it own the pipeline.

Reviewed the 2026 field (GitLab CI, Buildkite, CircleCI, Jenkins, TeamCity, Woodpecker/Gitea, Dagger, Argo/Tekton) against what this portfolio actually is: a GitHub-hosted monorepo, one operator plus coding agents, a self-hosted local platform behind TryCloudflare tunnels, and a signed-supply-chain ambition (S6). Verdict: GitHub Actions as orchestrator, with all pipeline logic extracted into a vendor-neutral contract that runs identically on your laptop — and a pull-based deploy instead of giving CI the keys to your machine.

01 What the decision actually depends on

Five facts about this project decide the answer, not feature lists: (1) the repo lives on GitHub, so anything else adds an integration seam; (2) the dev loop is local-first — your proof modules (check_* 27/27) already run on your machine, and CI must run the same commands, not a parallel YAML reimplementation; (3) the deploy target is your own host behind a tunnel, not a cloud k8s fleet; (4) S6 requires OIDC keyless signing (cosign) and attestations, which GitHub's OIDC issuer does natively; (5) a one-person + agents team can't afford to operate a CI server.

03 The Pipeline Contract (S5a) — the real decision

The lock-in and debuggability problems people leave Actions over come from writing logic in YAML. So the standard is: workflow YAML may only orchestrate; every step body is a just recipe (or script) that runs identically on your machine. CI becomes a thin scheduler around the same commands your loop and your agents already run.

# justfile — the pipeline IS these recipes; CI just calls them just lint # tokens hex-lint · py_compile · gitleaks just test # proof modules · contract tests · playwright smokes just build # vite build per surface just package # docker build + syft SBOM + cosign sign just smoke # curl every /health through the tunnel # .github/workflows/pipeline.yaml step bodies are ONLY: run: just <stage>

Consequences: local run = CI run (debug locally, never in YAML); swapping orchestrators (Woodpecker, GitLab, anything) is rewriting ~60 lines of glue, not the pipeline; and agents can execute any stage directly, which is how this project actually works.

04 Runner strategy — never give CI your house keys

Hosted runners: lint · test · build · package

Stateless stages run on GitHub-hosted runners (now including larger/ARM natively). Nothing secret beyond scoped tokens; OIDC mints short-lived identities for cosign — no long-lived signing keys stored anywhere.

Deploy: pull-based, from the host

Do not SSH from CI into your machine, and do not run a self-hosted runner exposed to a public repo (poisoned-PR risk). Instead the host pulls: a systemd timer (or watchtower) runs just deploy-pull — fetch latest signed images, cosign verify, docker compose up -d, then post a deploy receipt to the events plane. CI's deploy job just tags the release; the host decides to take it. That's GitOps' trust direction at compose scale, and it matches the house thesis: the artifact carries proof; the consumer verifies.

05 Hardening checklist (Actions-specific best practice)

  • Pin every third-party action by commit SHA, not tag — marketplace actions are a real supply-chain surface; Dependabot keeps the pins fresh.
  • Default-deny token: permissions: {} at workflow top; each job requests only what it needs (id-token: write only in package).
  • OIDC keyless everywhere — cosign signing and any cloud auth via the OIDC issuer; zero long-lived secrets in Actions beyond the gitleaks-scanned .env names.
  • Concurrency groups per ref to cancel superseded runs; path filters so design-only commits don't rebuild containers.
  • Cache aggressively (npm, docker layers) — the cheapest 40–60% build-time win.
  • Required checks as branch protection = the merge gate IS the standards gate (S1 lint, S4 proofs).
  • Flaky policy: quarantine within a day, fix or delete within a week — an ignored pipeline is worse than none (S10 honesty applies to CI too).

06 What changes in the standards

S5 is amended (recorded in production/standards/STANDARDS.md): GitHub Actions adopted as orchestrator; S5a Pipeline Contract (logic in just recipes, YAML orchestrates only); S5b pull-based deploy (host verifies signatures and pulls; CI never reaches into the host); hardening checklist absorbed into the workflow file. The existing production/ci/github-actions.yaml gets refactored to thin orchestration in its next touch. Decision is reversible by design — the contract makes the orchestrator a commodity.

Self-evaluation. The question wasn't "which CI is best" but "where should pipeline truth live" — answer: in the repo as runnable recipes, with Actions as the free, native scheduler and the host as the only party trusted to deploy to itself. Revisit triggers: leaving GitHub (→ Woodpecker/Gitea), outgrowing one host (→ Argo on k8s), or pipeline logic outgrowing shell (→ Dagger).
